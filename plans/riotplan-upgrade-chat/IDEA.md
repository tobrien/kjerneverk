# Idea: riotplan-upgrade-chat

## Core Concept

Upgrade rp_build from a one-shot LLM call to an agent-powered plan generation process that can explore the codebase, and leverage the project indexer to inject real code context into plan generation. The goal is to close the quality gap between plans generated by riotplan CLI and plans generated through Cursor, by giving rp_build the same codebase awareness that Cursor has.

## Initial Thoughts

- _Add your thoughts..._
- Two-pronged approach: (1) Auto-inject project index context into the generation prompt as a new == CODEBASE CONTEXT == section - this is cheap and gets immediate value. (2) Replace one-shot generation with agent-powered generation using AgentLoop + read-only file tools - this enables the LLM to explore code interactively during plan creation.
- The agent-powered build should use a new system prompt tailored for plan generation that instructs the LLM to: (1) explore the codebase using tools, (2) identify relevant files, interfaces, and patterns, (3) draft the plan with concrete references, (4) output structured JSON matching the existing GeneratedPlan interface.
- For the agent-powered approach, the plan output could be collected via a special `write_plan` tool that the agent calls when ready, rather than trying to parse a massive JSON blob from the text stream. This is cleaner and avoids JSON parsing issues.
- The existing `findProjectRoot()` in common.ts already walks up from plan path to find package.json - this same logic should be reused in rp_build to know where to index. The index is already cached in memory so if explore already indexed it, rp_build gets it for free.
- The end goal is IDE independence: `riotplan explore` from a bare terminal should produce the same quality plan as using RiotPlan through Cursor with Opus. The full lifecycle (explore → shape → build) must work end-to-end without an IDE. The build step is the biggest quality gap, but the entire flow needs to be validated as a standalone experience.
- Model quality matters. Cursor uses Opus (high-end model). The CLI currently defaults to claude-sonnet-4-20250514. For plan generation specifically, we should consider using a more capable model (opus) since plan quality is the primary output and this is a one-time cost per plan. The explore conversation can stay on sonnet, but rp_build might benefit from opus-level reasoning.
- Critical architecture insight: the explore agent already has read_file, grep, query_index tools. But when it calls rp_build, that tool runs a separate one-shot LLM call that has NONE of those tools. The fix is to make rp_build's internal generation inherit tools from its calling context. The tool execution context in wrapper.ts (line 133-158) passes workingDirectory but not the available tools. We need to thread tools through or detect them from the CLI environment.

## Constraints

- _Add constraints..._
- Must reuse the existing AgentLoop from @kjerneverk/agentic - no new agent framework
- Must use the existing project indexer (index_project/query_index) for codebase awareness - not build a new one
- Generated plans must include concrete file paths, class/interface names, and method references - not placeholders like "_List files that will be modified..._"
- Must maintain backward compatibility with the existing rp_build MCP tool interface - same parameters, same output files (SUMMARY.md, EXECUTION_PLAN.md, STATUS.md, PROVENANCE.md, plan/*.md)
- The agent-powered build should give read-only codebase access (read_file, list_files, grep, query_index) - no write access to project files during plan generation
- The project index should be built automatically before plan generation starts, taking no more than ~500ms for typical projects
- Must work both in CLI (riotplan explore → rp_build) and MCP server contexts - the build tool should detect available tools and use agent mode when file tools are available
- Must be language-agnostic - the project indexer and codebase context must work for Python, Rust, Java, C/C++, Go, Ruby, Swift, and .NET projects, not just Node.js/TypeScript
