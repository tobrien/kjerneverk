# Step 6: Design Cursor Rule Content

**Recommended Model**: Opus 4.5
**Rationale**: This is the second critical prompt engineering task. The Cursor rule must effectively suppress Cursor's own planning behavior ("this looks like a plan, want me to create one?") and keep the model focused on RiotPlan. The wording must be precise - too weak and Cursor ignores it, too aggressive and it breaks normal non-plan conversations. Requires deep understanding of how Cursor rules influence model behavior.

**Depends on**: Nothing (can run in parallel, but benefits from seeing Step 2's output)

## Objective

Design the content of a `.cursor/rules/riotplan.md` file that tells the model: RiotPlan owns planning in this project. Do not create Cursor plans. Do not implement unless explicitly asked.

## Background

Cursor has its own planning feature that detects when the user is working on something plan-like and offers to create a plan. This competes with RiotPlan. The user wants a Cursor rule that suppresses this behavior and defers to RiotPlan.

Additionally, the rule should reinforce the behavioral instructions from the tool descriptions (Step 2), providing a second layer of defense against mode drift.

## Tasks

- [ ] Draft the Cursor rule content
- [ ] Include instruction to defer to RiotPlan for all planning activity
- [ ] Include instruction to not create Cursor-native plans when RiotPlan is active
- [ ] Include instruction about stage transitions requiring user consent
- [ ] Include instruction about capturing insights in the plan, not just discussing them
- [ ] Specify when the rule applies (only when RiotPlan tools are being used? Always?)
- [ ] Consider using Cursor rule metadata (globs, description) to scope the rule
- [ ] Test by reading the rule as if you were a model - would you follow it?

## Design Considerations

- **Scoping**: Should this rule apply globally or only when in plan directories? Cursor rules support glob patterns.
- **Tone**: Assertive but not hostile. The rule is guidance, not punishment.
- **Specificity**: Should mention specific behaviors to avoid (creating checkbox plans, implementing without asking)
- **Coexistence**: Must not break normal Cursor usage outside of planning contexts

## Cursor Rule Format

```markdown
---
description: RiotPlan planning system integration
globs: ["**/plans/**"]
---

[Rule content here]
```

## Deliverable

A complete `.cursor/rules/riotplan.md` file content, ready to be generated by the tool in Step 7.

## Acceptance Criteria

- Rule content is clear, concise, and actionable
- Rule correctly suppresses Cursor's competing planning behavior
- Rule reinforces RiotPlan's behavioral instructions
- Rule uses appropriate scoping (globs/metadata)
- Rule does not interfere with normal Cursor usage outside planning
