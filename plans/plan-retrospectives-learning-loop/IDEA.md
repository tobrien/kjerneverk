# Idea: plan-retrospectives-learning-loop

## Core Concept

Generate retrospective.md as required plan output to capture what assumptions were wrong, where adaptation occurred, and feed learning back into future planning prompts for continuous improvement

## Initial Thoughts

- _Add your thoughts..._
- Core concept: retrospective.md as a required plan output that captures learning from execution
- Key questions retrospective should answer: wrong assumptions, adaptation points, specification quality (over/under), patterns for future plans
- Critical insight: retrospectives feed future planning prompts automatically - structured reflection instead of memory
- This creates continuous improvement for LLM collaboration - plans get better over time through learning loop
- Timing: retrospective generated at end of plan execution, as part of the process (not on-demand or per-milestone)
- Two-level reflection: (1) step-level self-reflection after each step execution, stored in STATUS.md (2) overall retrospective.md at plan completion
- Retrospectives are part of plan format, not a separate repository - they live with the plan
- Learning mechanism: when creating new plan, can point at other plans to learn from them (explicit reference, not automatic)
- Structure: freeform, not fixed schema - allows natural reflection rather than checkbox compliance
- Motivation: after 100+ plans, need feedback mechanism to improve both user behavior and system behavior
- Pattern: reasoning agents work best when they look back and understand what could have been done differently
- Step reflection timing: after step completes, with agent having memory of execution
- Step reflection content: time, deviations, surprises, blockers, PLUS "what could have been done differently to make it more straightforward"
- Critical: step reflections create inter-step communication mechanism - later steps learn from earlier reflections
- Overall retrospective synthesizes step summaries and compares original plan vs actual execution
- Retrospective is NOT a summary - it's high-value feedback: what went right, what went wrong, what could be done differently next time
- Retrospective should be creative - designed to improve future plan creation
- Learning from other plans: explicit during idea exploration ("consider retrospective from plan X"), not automatic detection
- Format: human-readable prose with YAML front matter (operational metadata)
- Broader insight: many RiotPlan files probably need YAML front matter (step status, plan status, etc.)
- When executing step N, agent must receive STATUS.md with all prior step reflections - this is the inter-step communication channel
- Triggering: riotplan_generate_retrospective command + automatic at last step completion + part of plan-complete workflow (all three)
- Referencing retrospectives: read file directly into context, NOT through evidence system. Must be wrapped with context about WHY it's being included
- Anti-pattern: templated/rote self-reflection ("if X then write Y"). Have seen this fail in commit message tools - produces predictable, low-value output
- Self-reflection must use genuine model reasoning - this is where LLMs should astound with creative insights we haven't considered
- Retrospectives demand the highest-tier model available - creative insight requires the most capable reasoning (e.g., Opus-class)
- Execution might pause before retrospective to allow switching to a higher-powered model
- Related but separate concern: multi-model execution (different models for different steps) - should be its own plan
- Current workflow: Opus 4.6 for plan creation, Haiku/Sonnet/Opus for step execution, then retrospective needs highest tier again
- Deliverable: Blog post 1 - "The Natural Model Tier Map" - create with high-tier, execute with variable tier, retrospect with highest tier
- Deliverable: Blog post 2 - "Self-Reflection in LLM Collaboration" - importance of genuine reasoning in reflection, anti-pattern of templated responses, creative potential of capable models reviewing their own work

## Constraints

- _Add constraints..._
- No automatic plan detection/indexing - explicit references only
- Step reflections must be accessible to subsequent steps during execution
- Overall retrospective must synthesize all step reflections
- YAML front matter standardization is out of scope - separate concern
- Reflections must be generated by real model inference, not templated logic or if-statement heuristics
- Prompt design for reflections must encourage creative, surprising, high-value insights - not checkbox compliance
- Retrospective generation should signal or allow for use of the highest-tier model available
- Multi-model execution is out of scope for this plan - separate concern
